# M13 AI 拍照识菜设计档

- 日期：2026-10-20
- 状态：设计待老大评审（未实现）
- 老大原话：「接入 deepseek api 支持识别我拍的图片通过我输入的重量来算出三大营养素以及热量，同时，扫描的食物会自动写进食物库方便下次直接使用」
- 四项裁决（2026-10-20 决策卡）：
  1. 入口：**两处都要**（记一笔弹层 + 我的食物库）
  2. 扫描后：**记账 + 入库都要**
  3. **菜名由老大手输**（模型只给建议预填）
  4. DeepSeek **key 已有**

## §0 前提核实（事实，有出处）

| 项 | 结论 | 出处 |
|---|---|---|
| DeepSeek 视觉 | `deepseek-flash` 支持图片：`content` 数组里放 `image_url` 块，三种传法（base64 data URL / 公网 URL / file_id），单图 ≤32 MiB、**≤1024 tokens** | 官方文档 `api-docs.deepseek.com/zh-cn/guides/vision` |
| 价格 | flash：输入 ¥1/M（未命中缓存）、输出 ¥4/M，高峰翻倍 | 官方 `quick_start/pricing` |
| 单次成本 | 1024 图 tokens + ≤300 输出 tokens ⇒ **约 ¥0.002/次** | 上两行推算 |
| 云函数现状 | `api-diet` Nodejs 18.15 / 256MB / **超时 20s** | MCP queryFunctions |
| 选图管道 | `image_picker` + `pickCompressedImageDataUrl`（原生侧 256px/q82）已存在 | `image_pick.dart:28` |
| 自定义食物存储 | 存「这一份」的量：`grams` + kcal/蛋白/碳水/脂肪；`per100` 由云端按份反推 | `index.js:82-92` |
| 客户端超时 | `ApiClient.defaultDio()` 三超时恒 15s | `api_client.dart:53-58` |

## §1 方案与取舍

| | 做法 | 结论 |
|---|---|---|
| **A** | 客户端压图 → 云函数内联调 `deepseek-flash` → 校验后返回 → 用户确认克数 → 写「食物库 + 当餐记录」 | ✅ 采用 |
| B | 云函数建异步任务 + 客户端轮询 | ❌ 多一张任务表与轮询，只为省几秒，YAGNI |
| C | 客户端直连 DeepSeek | ❌ key 打进 APK 等于公开 |

## §2 云函数

### 2.1 新路由 `POST /ai/food-scan`

```jsonc
// 请求
{ "image": "data:image/jpeg;base64,..." }      // ≤280_000 字符（与客户端同口径），仅 jpeg/png/webp
// 成功
{ "ok": true, "dish": "蒜薹鸡块", "confidence": "high|medium|low",
  "per100": { "kcal": 156, "protein": 8.6, "carb": 7.4, "fat": 9.8 },
  "note": "含较多油，估算仅供参考", "quota": { "used": 3, "limit": 50 } }
// 失败
{ "ok": false, "message": "今日识别次数已用完（50 次）" | "没认出来，换张更清楚的图" | "识别服务未配置" | ... }
```

- 调用参数：`model: deepseek-flash`、`temperature: 0.2`、`max_tokens: 300`、
  `response_format: {type: "json_object"}`（不支持时去掉，靠解析兜底）、超时 **12s**。
- Node 18 自带 `fetch`，**不新增依赖**。
- key 从函数环境变量 `DEEPSEEK_API_KEY` 读；缺失 → `{ok:false,message:"识别服务未配置"}`；
  **任何日志不得打印 key 与图片内容**。

### 2.2 服务端校验（不照单全收）

纯逻辑放 `api-diet/ai.js`（可 `node --test` 覆盖），`index.js` 只做胶水：

1. `parseModelJson(text)`：剥 ```json 围栏 / 前后杂字，取第一个完整 JSON 对象；失败返回 null。
2. `validateScanResult(obj)`：
   - `dish` trim 后 1–30 字
   - `per100.kcal` ∈ [0, 900]；`protein/carb/fat` ∈ [0, 100]，全部有限数
   - **能量一致性**：`|4P+4C+9F − kcal| / max(kcal,1) ≤ 0.25`，否则打回重试一次
3. 重试一次仍不合格 → `{ok:false, message:"没认出来，换张更清楚的图或手动填写"}`。
4. 入库值统一 `Math.round` 到 int/1 位小数，与现有自定义食物口径一致。

### 2.3 限流与成本

- 计数落 `sg_profiles` 现有文档：`aiScanDate` + `aiScanCount`（**不新建集合**，避免部署时还要建表）。
- 上限 `kAiScanDailyLimit = 50`/uid/天（最坏 ¥0.1/天）；命中上限直接返回文案。

### 2.4 新路由 `POST /foods/custom/upsert`

按**老大最终输入的菜名** upsert：
- `(uid, name)` 已有自定义条目 → 更新 kcal/三大营养素/grams/portion/meals/**image**；返回 `{ok,id,updated:true,emoji}`
- 与**内置库**同名 → **不写库**，返回 `{ok:true, skipped:"builtin",emoji}`，客户端提示「内置库已有「X」，本条未重复入库；要单独记请改个名字」
- 都没有 → 新增；返回 `{ok,id,created:true,emoji}`
- `emoji` 由服务端 `emojiFor(name)` 计算（与内置库同一张映射表），客户端记账时直接使用
- **`image` 随条目入库**（老大 2026-10-20 追加要求）：接收压缩后的 dataURL（与现有自定义食物同字段、同管道），
  服务端限 ≤280_000 字符且只收 `data:image/(jpeg|png|webp);base64,` 前缀；空串 = 无图（回退 emoji）
- `meals`：**新建时默认 `[]`**（未归类 = 全餐次可见，沿用现有规则）；**更新已有条目时不动它的 meals**（扫码没有归类意图，不能清空用户原有餐次标签）。要改餐次去食物库管理页点标签

### 2.5 超时调整

`api-diet` 超时 20s → **60s**（部署时 `updateFunctionConfig`）。客户端对该路由单独 30s 接收超时，
其余路由维持 15s（`ApiClient` 增加可选 timeout 参数，默认 null 不变）。

## §3 客户端

### 3.1 入口（两处）

1. **记一笔弹层**：搜索框右侧「📷」按钮（在「＋ 自定义」左边）；拍照/相册二选一（复用现有选图交互）。
2. **我的食物库**：底部按钮行加「📷 拍照添加」，与「＋ 添加自定义食物」并列。

两处共用同一个 `FoodScanSheet`。

### 3.2 选图

`pickCompressedImageDataUrl` 增加可选参数 `maxDim`（默认 256 不变）、`quality`（默认 82）、
`maxChars`（默认沿用 280000）。扫码用 **512px / q75**（约 40–70KB，base64 约 55–95K 字符）：用于识别。
取消选图 = 静默关闭，不报错。

**两张图分开（老大 2026-10-20 二次澄清）**：
- **识别图**：本次选的那张，只发给模型，决定返回的营养；不进食物库。
- **入库照片**：默认 = 识别图；可在确认页「从本地选一张」换成本地相册里的另一张
  （同样 **512px/q75**，与默认识别图同尺寸、观感一致），也可「移除」不存图。
- 换入库照片**不重新识别**（营养值不变），只影响入库与记账时携带的 `image`。

### 3.3 确认表单 `FoodScanSheet`

- 顶部：**入库照片**缩略图（默认=识别图；「从本地选」/「移除」两个小钮）+ `confidence` 提示
  （`low` 时黄字「识别把握不大，请核对菜名与数值」）。识别图本身在表单打开瞬间已用完，不再展示第二张
- 菜名：TextField，**预填模型建议**，可改（必填，1–30 字）
- 克数：数字输入（默认 **200g**，1–2000；不做步进钮，v1 以直接输入为主）
- 每 100g 四项：热量/蛋白/碳水/脂肪（可改，非负）
- 实时汇总：`这份 ≈ {kcal} kcal · 蛋白 {p}g / 碳水 {c}g / 脂肪 {f}g`（随克数/数值即时变）
- 按钮：「保存」（识别/保存中禁用并显示进行态）
- 入口差异：**记一笔入口**额外显示餐次（弹层上下文），保存 = 入库 + 记账；
  **食物库入口** = 只入库（无餐次上下文，避免记错时间）

计算落成纯函数 `scanPortionTotals(per100, grams)`：
`kcal = round(kcal100*grams/100)`，三大营养素各 `round1(x100*grams/100)`。

### 3.4 保存链（按此顺序，失败可解释）

1. `POST /foods/custom/upsert`（按最终菜名；`grams=克数`，营养按份，**image=入库照片**）= 入库
   - 返回 `skipped:"builtin"` → **不入库但照常记账**，toast「内置库已有「X」，本条未重复入库」
2. 失效 `foods.custom` 与搜索快照（`invalidateFoodLibrary`）
3. 记账入口：`addRecord`（复用 M11 乐观写入；`portion='${grams}g'`、`image=入库照片`、`emoji` 取 upsert 返回值）
   - 入库照片为空串时：`image=''`，行内回退 emoji
4. 入库成功但记账失败 → toast「已入库，本餐记入失败：…」，条目保留（不重复入库）
5. 入库失败 → 停留在表单并保留输入，可重试

### 3.5 失败与边界

| 情况 | 表现 |
|---|---|
| 断网/超时 | 弹「识别失败：网络异常」，可重试或转「手动填写」；不丢已选图 |
| 模型没认出来 / 校验不过 | 弹「没认出来，换张更清楚的图或手动填写」+「手动填写」跳转现有自定义食物表单 |
| 今日次数用完 | 提示 quota 文案，入口仍可手动记 |
| 图片过大 | 选图阶段按 `maxChars` 拒：「图片仍过大，请换一张」 |
| 用户取消 | 静默关闭 |

## §6 行为差异与风险登记

1. **两张图分开**（老大 2026-10-20 澄清）：**识别图**只发给模型、不落库；**入库照片**默认复用识别图，
   也可换成本地相册里的另一张（256px/q82，与现有自定义食物照片同管道），或移除（无图回退 emoji）。
   存储代价：入库图统一 512px，单条约 40–70KB。
   搜索快照会随条目数增长（M11-T1 本地化会带上自定义食物的 image）；实施时用真照片量实际字节，
   超预算就把默认入库图压到 256px。
2. **AI 数值是估算**：同菜不同做法偏差 20–30% 常见；表单标「AI 估算，可修改」，保存的以你确认的值为准。
3. **菜名决定一切**：「吃过 N 次」按菜名统计——同名会合并计数，这是特性；若你输的名字与内置菜同名，
   本条不入库（避免分裂计数），但照常记账。
4. **隐私**：识别图会发送到 DeepSeek（第三方）且不落云端；入库照片只存在你自己的 CloudBase 数据库
   （与现有自定义食物照片同等对待），不会发回给模型。
5. **超时风险**：网关是否允许 >15s 未验证；若实测 P95 超 12s，必须改异步（方案 B）——部署闸会量。

## §7 不做

- 多菜一图识别、菜品分割、重量估算（照片看不准克数，克数必须你输）
- 流式返回、识别历史、失败自动重拍
- H5 壳接入（H5 已停更在 1.4.0）
- 把 AI 结果当权威数据源（不做"自动记账不经确认"）
